House walkthrough

threepipe modelling editor, used as a newcomer would: a low-poly house from the start cube, with real keyboard and mouse input only (Playwright), once with the Blender keymap and once with the Design keymap. Branch demo-house-walkthrough at 7599f955. Driver: drive.mjs · findings: ux-findings.md.

What worked
  • The welcome asks one question (Blender or not) and the move-around cards follow the answer and the device.
  • Tab / Enter, 1-2-3, A, G/R/S with axis keys and typed values, E with typed distance: Blender muscle memory works, and the status strip shows the modal keys while you type.
  • Ctrl+R loop cut: the ring preview, the wheel for more cuts, the right click to keep it centred, exactly as in Blender.
  • The redo panel re-runs an operator with new values in one undo step; the History tab jumps to any step.
  • Knife: click points, Enter; one undo step. Save As downloads a .glb that re-opens with the same topology, editable.
  • Design keymap: the Scale and Move gizmo handles plus exact values typed in the redo panel build the same house; Shift + two-finger scroll orbits, two-finger scroll pans.
What did not
  • blockingThe mouse wheel and trackpad pinch do not zoom - filed (fix on three.js-modded branch fix/orbit-dolly-without-damping, awaiting a three-modded release; not worked around in the editor)
  • blockingDragging the Inset Faces / Bevel tool did nothing but stack toasts - fixed (2b51318, 7599f95)
  • blockingI then 0.1 switched to vertex select mode instead of setting the inset - fixed (2b51318, f5e481d)
  • blockingAfter typing a value in the redo panel, the viewport stopped taking keys - fixed (34ca389, add661b)
  • majorSnapping, pivot, orientation and proportional editing are placeholders in the header - filed
  • majorUp is Y; Blender tutorials say Z - filed (design decision for the maintainer)
  • majorThe Extrude tool on the shelf barely follows the mouse - filed
  • majorRepeated messages stack up as separate toasts over the model - filed

Findings, ranked

blocking

B1. The mouse wheel and trackpad pinch do not zoom

Tried
Scrolled the wheel over the viewport to get closer to the cube (Blender, Figma, Tinkercad: wheel or pinch zooms).
Happened
Nothing: three wheel notches (Blender run) or three Ctrl+wheel pinch events (Design run) leave the camera distance at 7.51 (run-*.json, step frame). Frame Selected / Frame All are the only zoom, and there are no zoom commands, keys or View menu entries either, so the demo zooms by framing.
Elsewhere
Blender: wheel, Ctrl+MMB drag, Numpad +/-, View > Navigation. Figma: pinch, Ctrl+wheel, Ctrl +/-. Tinkercad: wheel and +/- buttons on the view cube.
Where
three-modded examples/jsm/controls/OrbitControls.js:422 multiplies the dolly by (enableDamping ? dampingFactor : 0); the editor turns damping off at plugins/modelling-editor/src/EditorViewportPlugin.ts:141. No zoom operators: plugins/modelling-editor/src/ops/viewOps.ts.
Issue
issues/open/modelling-tools/ux-wheel-zoom-dead.md
issues/open/modelling-tools/ux-no-zoom-commands.md
Status
filed (fix on three.js-modded branch fix/orbit-dolly-without-damping, awaiting a three-modded release; not worked around in the editor)
blocking

B2. Dragging the Inset Faces / Bevel tool did nothing but stack toasts

Tried
Selected a gable face, clicked Inset Faces on the tool shelf and moved the mouse to set the thickness, as its tooltip says.
Happened
The thickness never changed; every mouse move posted another "Finish the current operation first" toast (five on screen at once). The modal re-runs its operator through the redo path, and the operators refused to run while a modal was active - including the modal itself.
Elsewhere
Blender: Inset Faces follows the mouse live (edbm_inset_modal), so does Bevel; the header shows the value.
Where
plugins/editor-engine/src/ops/messages.ts:17 (notModalMessage refused engine.propDrag), called on every re-run from plugins/editor-engine/src/tools/PropDragModal.ts _apply.
Status
fixed (2b51318, 7599f95): the modal's own re-runs pass (PropDragModal.applying), and the shelf tool runs on a press-drag-release in the viewport as Blender's does - before that, the reference was taken where the pointer crossed into the viewport and the first driver run got an inset of 1.87 that turned the gable wall inside out. e2e: modelling-editor-inset-bevel, section 3.
blocking

B3. I then 0.1 switched to vertex select mode instead of setting the inset

Tried
Blender muscle memory for the door: I, type 0.1, Enter.
Happened
I inset instantly at 0.05 with no modal; the typed 1 then switched to vertex select mode (and 2 would have picked edge mode), Enter did nothing. Ctrl+B was the same. The redo panel was the only way to get an exact value.
Elsewhere
Blender: I and Ctrl+B are modal; the mouse distance from the selection centre sets the value, digits type it (handleNumInput), Enter confirms, Esc cancels; I / O / B toggle individual / outset / boundary while it runs.
Where
plugins/editor-engine/src/keymap/presets/blender.ts:88-89 (before the fix) bound I and Ctrl+B to the instant operators; PropDragModal had no numeric input (its docstring said "digits type the value", handleKey had none) and mapped horizontal mouse travel instead of Blender's distance from the centre.
Status
fixed (2b51318, f5e481d): I and Ctrl+B start the inset/bevel modal in both presets; PropDragModal ports edbm_inset_modal / edbm_bevel_modal (NumInput, radial mouse mapping, Shift precision, I/O/B toggles). Typing a width that starts with 0 ran a bevel of width 0, which errored ("indices is not iterable": the bevel command returned newFaces: 0) and cleared the selection; fixed in the command, the reselect and the modal. e2e: modelling-editor-inset-bevel, sections 1, 2, 4; unit test in plugins/modelling/tests/undo-fidelity.test.ts.
blocking

B4. After typing a value in the redo panel, the viewport stopped taking keys

Tried
Set the inset thickness to 0.1 in the redo panel, pressed Enter, moved back over the house and pressed S X 0.6 to narrow the door.
Happened
Nothing happened: the number field kept the focus after Enter, so S, X and the digits went into it. Getting the keys back took a click in the viewport, which changes the selection. Typing a value also re-ran the operator on every keystroke (0, 0., 0.1), and the field was disabled while each re-run ran, which could drop keystrokes into the viewport as select-mode switches. A ticked checkbox kept the keys the same way.
Elsewhere
Blender: keys go to the area under the pointer (wm_event_system.cc:4400); a number field applies on Enter and ends its editing. Figma: Enter commits a field and returns to the canvas.
Where
plugins/modelling-editor/src/ui/PropsForm.tsx (NumericInput onValueChange committed per keystroke, focus kept after Enter); plugins/editor-engine/src/input/InputRouter.ts (routing by document.activeElement only).
Issue
issues/open/modelling-tools/ux-keys-after-redo-panel.md (filed by the parent on modelling-editor)
Status
fixed (34ca389, add661b): number fields commit on Enter or blur and end editing on Enter/Esc; the viewport takes the keys back when the pointer is over it unless a text field is being typed into. e2e: modelling-editor-panel-keys (fails with the router change taken out).

M2. Up is Y; Blender tutorials say Z

Tried
G Z 0.7 to lift the ridge, E Z 0.5 for the chimney, as every Blender tutorial types.
Happened
Z is depth here (three.js / glTF Y-up), so the ridge would move towards the viewer. The view gizmo shows Y on top and the status strip lists X / Y / Z, so G Y works once you notice.
Elsewhere
Blender is Z-up; Figma has no third axis; Tinkercad is Z-up on its workplane.
Where
plugins/mesh-edit/src/transform/keymap.ts:47-53 (axis keys map to the world axes as named).
Issue
issues/open/modelling-tools/ux-axis-keys-y-up.md
Status
filed (design decision for the maintainer)
