# Modelling and procedural generation in threepipe — roadmap, October 2026

**Status**: proposed 2026-10-16, for Palash's review. Parent: [10-editor-plan](./10-editor-plan.md) (editor),
[00-synthesis](./00-synthesis.md) (modelling), `issues/open/procedural-generation-status.md` on branch `proc`
(procedural). Landscape since mid-September: [research-landscape-2026-10](./research-landscape-2026-10.md),
which extends [research-ai-3d-ecosystem](./research-ai-3d-ecosystem.md) (September).

## 0. The short version

1. **Nothing of this work is shipped.** Modelling (five packages, ~85k lines, Blender ports with fixtures,
   a working editor and agent harness) sits on `modelling-editor`, 173 commits off `dev`, with one stale PR
   (#41) against the wrong base. Procedural generation sits on a local, unpushed, seven-month-old branch
   (`proc`) and is gitignored in the main checkout. Track 0 is to land both.
2. **Since September the field converged on one agent packaging**: a JSON command API, a CLI whose verbs
   each return one JSON object, a `look` tool that renders multi-angle sheets, a `SKILL.md`, and a Claude
   Code plugin (mcp-for-blender 2.x with nine tools, nodebpy, img2threejs at 18k stars, glb-buildings-skill,
   agentcad). We have the command API and the session harness; the rest is a small track with the highest
   leverage per day (Track 1).
3. **Someone has shipped Blender geometry nodes running in three.js** (`ProceduralBuildingsThreeJS`, MIT,
   Sept 24–28, 60 node types, per-asset evaluator over JSON dumps, verified against Blender within 2 mm)
   and a second clean-room evaluator started (`geonodes-kit`, 360-node inventory for 5.2.2, two nodes
   verified). Neither is reactive, general or editable. Our `proc` branch did the same thing in March
   on three ad-hoc triangle formats, before the kernel existed. The move is to rebuild it on
   `mesh-kernel`'s `MeshData`, which already mirrors Blender's `Mesh` attribute domains, so geometry nodes
   become a live modifier on an editable mesh. Nobody has that (Track 2).
4. **The evidence on verification hardened**: EditHero (Oct 1) shows code-editing agents preserve unedited
   parts far better than regenerating models but take minutes per edit; WorldBench (Oct 7) shows a judge
   reading only code gave full credit for four of five deleted features; LEGO-Anything (Sept 28) finds
   agents' self-evaluation unreliable. So `measure` / `validate` / `diff` (edit locality) come before more
   operators, and an EditHero-style chain harness becomes our regression suite.
5. **Blender 5.3** (release ~Nov 10) makes LoopTools Relax / Curve / Gstretch native C++ operators and adds a
   Quad-Sphere; port those. Pin the geometry-nodes port to **5.2 LTS** (we have its source in
   `.repos/blender-gn-source`; 5.3 adds list sockets and Construct Curves that are still moving).
6. **three.js** r186 changes nothing for procedural geometry; WebGPU/TSL are not prerequisites for any of
   this. The r168 → r177 upgrade PRs (#42, #45) should land *after* the modelling merge, whose core diff is
   134 lines.

Decisions needed (recommendations in bold): D13 ship order (**modelling → dev before the three
upgrade**), D6 booleans (**manifold-3d, Blender's own exact solver since 4.5**), D14 geometry-nodes
Blender pin (**5.2 LTS**), D15 enum spelling (**Blender RNA names, `'INVERSE_SQUARE'`**), D16 push the
`proc` branch (**yes, as `procgen-archive-2026-03`, before anything is rebuilt**).

### Track 1 — Agent packaging (2–3 weeks, one agent, in parallel with Track 0 step 3+)

What the field converged on, built over the existing command registry (`plugins/modelling/src/commands`,
49 ops) and `scripts/modelling-session.mjs`:

1. **`look`** command: multi-angle sheet (auto-framed front/side/top/iso), `camera` / `view` / saved

2. **Measured checks before renders**: `measure` exists; add `validate` (port `bmesh_mesh_validate.cc`,

3. **CLI** `@threepipe/modelling` (`npx threepipe-modelling run cmd.json | session build.mjs | look | export`),
   one JSON object per verb on stdout, like agentcad and glb-buildings-skill.
4. **`SKILL.md` + `.claude-plugin`** generated from the registry (`help` already describes commands): workflow
   order (build → measure → validate → look → export), the anti-mistake list, a task-indexed cookbook from

5. **Replay**: `tmp/eiffel-live` becomes a committed example that replays any `transcript.json`; add a

6. **Chain harness** ("BMeshBench", from the September survey, now with EditHero as the published
   precedent): start mesh + instruction + expected `measure`/locality; seed with 20 tasks cut from our own
   builds and the kernel fixtures. This is the regression suite for everything below.
7. **Import bridge**: `document.importObject(three.Object3D | glTF)` → editable `MeshData` with weld
   (the edit-mode entry path already does this), so img2threejs-style generated code lands as editable
   topology.
8. Last, a thin MCP wrapper over the same registry (the blueprint editor's bridge already relays tool lists).

### Track 2 — Procedural generation on the kernel (6–8 weeks for the first usable subset)

Goal: Blender geometry nodes, ported from 5.2 LTS source, evaluated live in the browser and in Node on
the same `MeshData` the modelling tools edit, exposed as a modifier and as a typed TS graph API that
agents write as code.

1. **Data model** (subplan): geometry set = `{mesh: MeshData, pointCloud, curves, instances}` with
   attribute domains point / edge / face / corner / curve / instance; **fields** as lazy functions over a
   domain with Blender's implicit interpolation rules (`attribute_math`, `GeometryFieldContext`); no
   ad-hoc `PrimGen`/`MeshOps`/points formats. Lists and dynamic sockets kept in mind for 5.3+.
2. **Runtime**: keep the `proc` branch's dirty-propagating pull evaluator and auto-UI; add Blender's
   lazy-function semantics (only evaluate what an output needs), repeat/simulation zones later.
3. **Nodes, by the three universal patterns** (plan v3 on `proc`): classify faces, distribute → instance,
   displace → derive. First ~40 nodes: inputs (position, normal, index, ID, named attribute, face area,
   edge angle), math / vector math / compare / map range / random value (fixing the audited divergences),
   noise / voronoi / white noise (Blender's exact hashes), mesh primitives (reuse the kernel generators),
   set position, extrude mesh (kernel `extrude`), subdivide / subdivision surface, merge by distance (kernel),
   distribute points on faces (existing exact port), instance on points, realize instances, join, separate,
   delete geometry, transform, capture / store / evaluate on domain, curve resample / to mesh / to points,
   mesh boolean (manifold-3d), switch / index switch, accumulate field / evaluate at index.
4. **Graph as code**: TS DSL mirroring nodebpy's shape; import of JSON dumps (our `extract_geo_nodes.py`
   already produces them; nodebpy and NodeToPython as alternatives); agents write the DSL, not raw
   node-link JSON (both surveys: constrained graphs are the only ones that worked).
5. **Modifier**: a `geometryNodes` modifier in `plugin-modelling`'s stack beside array and mirror, with its
   inputs in the editor's modifier panel; applying it bakes to `MeshData` like Blender's Apply.
6. **Verification**: the existing ground-truth pipeline (headless Blender exports, `compare_graph.ts`),
   per-node parity fixtures as in mesh-kernel, a reactivity perturbation test per graph; the Buildify,
   flower, pebble and terrain examples re-pass on the new runtime. Cross-check against
   `geonodes-kit`'s node inventory and `ProceduralBuildingsThreeJS`'s verify scripts (read, do not copy).
7. **Package**: `@threepipe/plugin-procedural` (new name; the old one is unpublished), Node-safe like the
   kernel; the 21 examples move in with their assets.

geometry representation beside `MeshData`, and no render-only verification.

## 6. Realism: targeting real results (2026-10-18, after Palash's review of the demos)

### What the demos showed

The demos are good tests of the API (measured, reactive, manifold, 0 failed commands) but the results
are low-poly blockouts, not usable models. The camera demo picked the same camera as our 2021 webgi demo
(https://camera-webgi.vercel.app/, Canon 5D Mark IV + EF 24-105 f/4L), so that demo's `camera.glb` is a
ground truth. Rendered side by side in the **same plain threepipe viewer** (same HDRI, no webgi
post-processing; `.repos/status/ref/plain-side-by-side.png`), theirs reads as a real camera and ours as a
toy. **The gap is the model, its materials and its markings, not the renderer.**

What makes the reference real (`camera.glb`: 94 meshes, 136k triangles, 26 materials, 8 textures):
1. **Form language**: every surface is a subdivision surface with tight creases - the prism hump, grip and
   body are soft and continuous; no flat box faces; every edge has a chamfer that catches a highlight.
2. **Detail density**: dozens of buttons, port doors, panel gaps (a dedicated `GapsColor` material),
   screws, the knurling profile, the lens element stack.
3. **Materials**: rubber and leather/plastic grain bump maps, a spread of roughness on near-black surfaces,
   metal, see-through glass and screens (transmission on 4 materials). Clearcoat and iridescence are declared
   but zero on all 26 (corrected by the realism track's measurements, `16-realism.md` §1.4).
4. **Markings**: label textures for every print - "EOS 5D Mark IV", "24-105mm 1:4 L", the top LCD and
   rear screen content, button icons. Ours has no text at all.

### The approach from here

- **High poly is the source of truth; low poly is derived** (decimate + normal-map bake), not modelled
  separately. The current demos become LOD blockouts at best.
- **Agents should not hand-build what a library can supply.** The camera took 189 active minutes, 262 tool
  calls and 308 low-level commands, much of it computing profiles and placing primitives by hand.
